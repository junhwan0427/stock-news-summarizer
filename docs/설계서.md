# 미국 주식 관심 종목 뉴스 요약 + 예측 프로젝트 설계서

> 작성 시작: 2026-09-24
> 목적: 신입 개발자로서 초기 세팅부터 배포까지 A~Z를 직접 설계하고 구현해보는 사이드 프로젝트.
> 이 문서는 "무엇을 골랐는지"와 "왜 골랐는지, 무엇과 비교했는지"를 함께 남긴다.

---

## 1. 프로젝트 목표

> 2026-09-24 무게중심 변경: "예측 프로그램"에서 **"관심 종목 뉴스 요약 서비스 + 예측 실험"**으로.

**주인공: 관심 종목 뉴스 요약.** 사용자가 등록한 관심 미국 주식 종목의 뉴스를 매일 모아서, LLM이 핵심 기사를 고르고 요약한다. 사용자는 **자기가 정한 시간에** 요약을 알림으로 받는다. 예측이 틀려도 이건 매일 쓸모가 있다.

**실험 기능: 예측.** 같은 뉴스로 "오를지 / 내릴지 / 중립"을 예측하고 근거를 남긴다. 다음 날 실제 주가와 비교해서 적중률을 누적한다. 포지셔닝은 "실험"이지만 **구현은 제대로 한다.** LLM 연동, 채점, 적중률 분석, 그리고 최종적으로 Llama 파인튜닝까지.

**최종 목표**: 쌓인 데이터로 Llama를 파인튜닝해서 내 전용 분석 모델을 만든다.

### 현실 체크

뉴스만으로 하루 주가 방향을 안정적으로 맞히는 모델은 없다. 뉴스는 몇 분 안에 가격에 반영되고, 하루 등락엔 잡음이 크다. 적중률 55%도 잘한 것.
그래서 예측의 가치는 "맞느냐"가 아니라 **"의미가 있는지를 정직하게 측정하는 시스템"**에 있다. 면접에서 "주가 맞히는 AI"가 아니라 "요약 파이프라인 위에 예측 실험을 얹고 결과를 측정했다"로 말한다.

## 2. 전체 흐름 (파이프라인)

> 아키텍처·인프라·데이터 흐름·ERD 그림은 [구성도.md](구성도.md) 참고.

```
[저녁 분석 작업] KST 20:00 (그날 밤 미국 장이 휴장이면 건너뜀)
    │
    ▼
[종목 목록 조회] 활성 종목
    │
    ▼
[뉴스 수집] Polygon → 종목별 "마지막 요약 이후" 기사 → 새 기사만 저장 (URL 중복 체크)
    │
    ▼
[분석 요청] Spring Boot → (HTTP) → Python 분석 서버
    │                                   │
    │                        처음: Claude API 호출
    │                        나중: 파인튜닝된 Llama 호출
    │                                   │
    ▼◄──────────────────────────────────┘
[저장] 요약(핵심 기사 + 요약 문단) + 예측(방향 / 확신도 / 근거) + LLM 응답 JSON
    │
    ▼
[발송 작업] 사용자별 알림 시간에 관심 종목 요약 발송

[아침 채점 작업] KST 07:00 → 방금 닫힌 미국 장의 일봉 조회 → 예측 적중 여부 기록 (휴장일이면 건너뜀)
```

별도로, **과거 데이터 백필(backfill)** 기능을 한 번 실행해서
과거 1~2년치 뉴스와 주가를 미리 저장한다. 이건 Llama 학습용 교재이며 Claude를 거치지 않는다.

## 3. 설계 결정 기록

각 항목은 [결정] → [비교한 것] → [왜] 순서로 적는다.

### 3-1. 백엔드 언어 / 프레임워크

- **결정**: Spring Boot (Java)
- **버전과 세부** (2026-09-27):
  - Spring Boot **4.1.1**, Java **21**. 비교: 3.x(회사 코드와 같지만 무료 지원 종료, Initializr가 더 이상 제공 안 함) vs 4.x(신규 프로젝트 표준, Jackson 3 등 변경점 있음). Java는 LTS 중 이미 설치돼 있고 실무에서 가장 많이 쓰는 21. 25는 최신 LTS지만 자료가 적다.
  - 빌드 설정 문법: **Gradle Groovy**(`build.gradle`). 비교: Kotlin DSL(`build.gradle.kts`, 타입 검사·자동완성이 정확, Gradle 공식 기본값). 빌드 파일은 라이브러리 몇 줄 추가하는 수준이라 Kotlin 장점이 크지 않고, 회사 코드·예제와 모양이 같은 Groovy.
  - 패키지: **`io.github.junhwan0427.stocknews`**. 도메인이 없을 때 GitHub 주소(`junhwan0427.github.io`)를 거꾸로 쓰는 관례. 실제 소유 주소라 절대 겹치지 않는다. 비교: `com.stocknews`(짧지만 남의 도메인), `com.stockpredict`(예측 중심 시절 이름).
  - 시작 라이브러리: Web(MVC), Data JPA, PostgreSQL Driver, Flyway, Validation, Testcontainers. 설계서에서 이미 정한 것만. Lombok 등은 미정.
- **비교**: Python(FastAPI) 단독 vs Spring Boot
- **왜**:
  - 회사 스택(Vue/React + Spring Boot)과 같아서 배운 게 한 방향으로 쌓인다.
  - "LLM이면 파이썬"은 오해. 모델을 학습시킬 때 파이썬이 필요한 것이고, API 호출은 HTTP 요청일 뿐이라 어떤 언어든 된다.
  - 이 프로젝트의 어려운 부분은 언어가 아니라 구조 설계다.

### 3-2. LLM 사용 방식

- **결정**: 처음엔 Claude API, 나중에 파인튜닝한 Llama로 교체. 호출부는 `interface`로 분리.
- **비교**: Claude API vs 학습 안 한 Llama(Ollama 로컬) vs 처음부터 Llama 파인튜닝
- **왜**:
  - 파인튜닝은 "뉴스 → 다음 날 실제 주가" 교재가 최소 수백 건 필요한데 지금은 0건.
  - Claude는 첫날부터 쓸 만한 판단을 내려주고, 기사 분류 라벨도 붙여줘서 교재 품질을 높인다.
  - Claude의 적중률이 나중에 내 Llama와 비교할 기준선(baseline)이 된다.
  - 로컬 Llama는 6GB GPU에선 작은 모델만 돌아가 판단 품질이 떨어진다.
  - 비용: Opus 5 기준 종목 5개 × 기사 10개/일 ≈ 월 $6 수준. 선불 충전 방식.

### 3-3. 파이썬의 역할

- **결정**: FastAPI로 "분석 서버"를 따로 둔다. Spring Boot가 HTTP로 호출.
- **비교**: FastAPI vs Django vs Flask / 파이썬 없이 Spring Boot 단독
- **왜**:
  - 나중에 Llama를 실행/학습하는 도구가 전부 파이썬이라 어차피 파이썬 서버가 필요하다.
  - "두뇌"를 서버 단위로 분리하면 Claude → Llama 교체 시 Spring Boot는 손댈 게 없다.
  - Django는 풀세트라 과하고, DB를 자기가 관리하려 해서 Spring Boot와 충돌 소지. Flask는 구식.
  - FastAPI는 API 서버 전용이라 역할에 딱 맞고, 요청/응답 형식 검증과 문서 자동 생성이 된다.
  - 감수할 것: 서버가 둘이라 실행/관리 포인트가 둘. Docker Compose로 묶어서 해결.

### 3-4. DB

- **결정**: PostgreSQL. 쓰기는 Spring Boot만, 읽기는 Spring Boot와 Python 둘 다.
- **비교**: PostgreSQL vs MySQL vs MongoDB vs SQLite
- **왜**:
  - 종목-기사-요약-예측-결과가 서로 연결된 데이터라 조인이 많다 → 관계형 DB. MongoDB 탈락.
  - SQLite는 서버 두 개가 동시에 쓰기엔 부적합 → 탈락.
  - MySQL도 가능하지만, LLM 응답(모양이 계속 바뀌는 JSON)을 JSONB로 저장하고 검색/인덱스까지 되는 PostgreSQL이 더 편하다.
  - 파이썬 데이터 분석 도구와 궁합이 좋고, 클라우드 무료 티어도 많다.
  - 쓰기를 한 곳(Spring Boot)에 몰아야 데이터가 꼬이지 않는다.
- **버전**: PostgreSQL 17 (Docker 공식 이미지 `postgres:17`).
  - 비교: 17 vs 18. 18은 최신이지만 Docker 이미지의 데이터 저장 경로 규칙이 바뀌어 옛 예제대로 볼륨을 걸면 막힌다. 처음 Docker를 다룰 때는 예제와 똑같이 동작하는 17이 배우기 편하고, 17도 몇 년간 지원된다.

### 3-5. 뉴스 API / 주가 API

- **결정**: Polygon.io (2026년 현재 Massive로 리브랜딩) 하나로 뉴스 + 주가 모두 처리. 보조로 Finnhub.
- **비교**:

| API | 무료 티어 호출 제한 | 뉴스 과거 범위 | 주가 과거 범위 | 비고 |
|---|---|---|---|---|
| **Polygon (Massive)** | 5회/분 | 2년 | 2년 (일봉) | 종목별 뉴스, 기사에 감성 분석 포함, 1회 최대 1000건 |
| Finnhub | 60회/분 | 1년 | 제한적 | 종목별 뉴스, 호출 여유 많음 |
| Alpha Vantage | **25회/일** | 2022-03 이후 | 무료는 최근 100일만 | 호출 제한이 너무 빡빡 |
| NewsAPI | 100회/일 | **1개월** | 없음 | 24시간 지연, 개발용만 허용 |
| yfinance (Yahoo) | 비공식 | 없음 | 20년+ | 비공식이라 언제든 막힘, 파이썬 전용 |

- **왜**:
  - 백필에 필요한 "과거 뉴스 + 과거 주가"를 **API 키 하나**로 2년치 확보 가능.
  - 5회/분은 느리지만, 뉴스는 1회에 1000건까지 받아서 종목당 몇 번이면 1년치가 끝난다. 일봉도 종목당 1회.
  - 매일 실행 시 종목 5개 × 2회 = 10회, 2분이면 충분.
  - 기사마다 감성 분석(insights)이 붙어 있어 Llama 학습 교재의 라벨로 활용 가능.
  - NewsAPI는 1개월 제한이라 백필 불가. Alpha Vantage는 하루 25회라 백필에 며칠씩 걸림.
  - yfinance는 공식 API가 아니라 갑자기 막히면 파이프라인이 죽는다. 사이드 프로젝트라도 이 위험은 피한다.
  - Finnhub는 호출 여유가 커서, Polygon 뉴스가 부족할 때 보조 소스로 쓴다.

### 3-6. Llama 학습 환경

- **결정**: 학습은 Google Colab(무료 GPU 16GB), 실행은 내 PC에서 Ollama.
- **내 PC**: GTX 1660 SUPER, VRAM 6GB
- **왜**: 6GB로는 Llama 8B 파인튜닝 불가(최소 8GB+). 실행만은 양자화 모델로 가능.

### 3-7. 스케줄러

- **결정**: Spring 내장 `@Scheduled` + `job_runs` 테이블 + 앱 시작 시 밀린 작업 따라잡기 로직. 수동 실행 API 별도 제공.
- **비교**: `@Scheduled` vs OS 스케줄러(cron, Windows 작업 스케줄러) vs Quartz
- **왜**:
  - `@Scheduled`는 한 줄이면 되고 스케줄이 코드 안에 있어 Git에 남는다.
  - OS 스케줄러는 설정이 코드 밖에 있어 Git 관리가 안 되고 PC를 바꾸면 재설정해야 한다.
  - Quartz는 미스파이어(놓친 실행) 처리와 분산 실행을 내장하지만, 서버 한 대에 작업 몇 개인 지금 규모엔 과하다.
  - "앱을 매번 켜두지 않을 수 있다"는 요구는 `job_runs` 테이블에 마지막 성공 날짜를 기록하고 앱 시작 시 빠진 날짜를 계산해 돌리는 것으로 해결. 20~30줄짜리 로직이다.
  - **Quartz 전환 시점**: 작업이 수십 개로 늘거나, 서버를 두 대 이상 띄우거나, 스케줄을 DB에서 바꾸고 싶어질 때. `job_runs`는 그때도 필요하므로 지금 만드는 게 낭비가 아니다.
- **작업 종류** (`job_runs.job_name` 값):
  - `DAILY_ANALYSIS` 저녁 분석, KST 20:00, 미국 장 열리기 전. 뉴스 수집 → 요약 + 예측 생성. LLM 호출 한 번으로 둘 다 나온다.
  - `SCORE` 아침 채점, KST 07:00, 장 닫힌 뒤. 일봉 수집 → 채점.
  - 발송 작업: 30분마다 깨어나 "지금 받을 사용자"에게 이미 만들어진 요약을 보낸다. 세부 규칙은 3-9. **`job_runs`에는 기록하지 않는다.** 하루 48번 돌고 대부분 "보낼 사람 없음"이라 작업 일지만 어지럽힌다. 발송 이력은 `notification_logs`가 전부 갖고 있다.
  - `COLLECT` 뉴스·일봉 수집만. 따라잡기에서 쓴다.
  - `BACKFILL` 과거 데이터 일괄 수집. 최초 1회 수동.
- **같이 정한 것**:
  - `@Scheduled`에 `zone = "Asia/Seoul"` 명시. 안 하면 클라우드(UTC) 배포 시 9시간 밀린다.
  - 작업은 **멱등**하게. 같은 날짜로 두 번 실행해도 중복 생성 없이 건너뛴다.
  - `POST /jobs/{name}/run?date=` 형태의 수동 실행 API. 개발 중 시간 안 기다리고 테스트.
  - **대상 날짜(`target_date`)**: 저녁 분석의 대상은 그날 밤 열리는 미국 장이고, 그 미국 날짜는 KST 날짜와 같다. 아침 채점의 대상은 방금 닫힌 미국 장, 즉 KST 기준 어제 날짜.
  - **휴장일**: 주말과 미국 공휴일은 휴장. 대상 날짜가 휴장이면 분석·예측·채점을 모두 건너뛰고 `job_runs`에 `SKIPPED`로 기록한다. 실패가 아니다. 휴장일 목록은 Polygon 시장 휴일 API로 받는다. 무료 요금제 제공 여부는 세팅 때 확인.
  - **뉴스 수집 범위**: 종목별로 "마지막 요약 이후 전부". 첫 요약이면 최근 24시간. 고정 24시간으로 하면 월요일 요약에 주말 뉴스가 빠진다.
- **따라잡기 규칙** (데이터 누수 방지):
  - 채점, 뉴스 수집, 주가 수집: 밀린 날짜 전부 따라잡음. 휴장일은 건너뜀.
  - 요약·예측: **따라잡지 않음.** 뒤늦게 만든 예측은 그 사이 뉴스에 결과가 섞여 있어 적중률을 오염시킨다. 놓친 날은 "요약 없음"으로 남긴다.

### 3-8. 벡터 DB

- **결정**: 별도 벡터 DB 도입 안 함. 필요해지면 PostgreSQL의 pgvector 확장 사용.
- **비교**: 별도 벡터 DB(Pinecone, Chroma 등) vs pgvector vs 안 씀
- **왜**:
  - 초기엔 뉴스 수집 → 요약·예측 → 채점 파이프라인이 우선이라 벡터 검색이 필요 없다.
  - 나중에 "오늘 뉴스와 비슷한 과거 뉴스 사례"를 찾아 프롬프트에 넣는 RAG를 할 때 필요해질 수 있다.
  - 그때도 pgvector면 기존 PostgreSQL 안에서 해결되어 서버를 하나 더 띄우지 않아도 된다.

### 3-9. 알림

- **결정**: 개발/테스트 단계는 텔레그램, 운영 단계는 카카오톡. 알림은 `interface`로 분리해 구현체를 갈아끼운다.
- **비교**: 텔레그램 봇 vs 카카오톡 "나에게 보내기" vs 슬랙 웹훅 vs 이메일
- **왜**:
  - 텔레그램은 봇 토큰 하나면 만료 없이 HTTP 요청 한 번으로 끝. 개발 중 빠르게 확인하기 좋다.
  - 카카오톡은 실제로 매일 보는 앱이라 운영엔 이게 맞다. 대신 액세스 토큰이 몇 시간마다 만료되어 리프레시 토큰 자동 갱신 로직이 필요하다. 이건 OAuth 연습으로 가치가 있다.
  - 슬랙은 개인용 워크스페이스를 따로 만들어야 하고, 이메일은 SMTP 설정이 번거롭고 폰에서 보기 불편.
  - `Notifier` 인터페이스 아래 `TelegramNotifier`, `KakaoNotifier` 구현체를 두고 설정으로 선택.
- **사용자별 알림 시간**: 사용자마다 요약 받을 시간을 정한다. 요약은 저녁 분석에서 종목당 한 번만 만들고, **발송만** 사용자별 시간에 나눠서 한다. 사용자마다 따로 만들면 Claude 비용이 사용자 수만큼 는다. `users.notify_time` 컬럼과 `NOTIFY` 작업으로 구현.
- **알림 시간 세부 규칙**:
  1. **시간 범위 제한 없음.** 아무 시간이나 고르고, 그 시점에 종목별로 **가장 최근 요약**을 받는다. 메시지에 요약 생성 시각을 같이 적는다. 아침에 받는 요약도 뉴스 정리로는 쓸모가 있고, 원래 목적이 "내가 정한 시간에"였다. 비교안: 저녁 8시~장 열리기 전만 허용(요약·예측이 가장 의미 있는 시간이지만 선택 폭이 두 시간뿐).
  2. **30분 단위.** `NOTIFY` 작업이 30분마다 깨어나 "알림 시간이 지났고 오늘 아직 못 받은 사용자"를 찾는다. 1분 단위면 매분 깨어나야 한다.
  3. **중복 방지는 발송 기록 테이블로.** `notification_logs`에 시도마다 기록하고, "사용자 + 발송 날짜"에 **성공은 하나만** 허용하는 부분 유니크 인덱스를 건다. 실패한 시도는 여러 번 남을 수 있고, 다음 30분에 다시 시도된다.
  4. **놓친 발송은 같은 날 안에서만.** 앱이 꺼졌다 켜지면 발송 작업이 바로 한 번 돌아서, 오늘 알림 시간이 이미 지났는데 못 받은 사용자에게 늦게라도 보낸다. 날짜(KST)가 바뀌었으면 보내지 않는다. 하루 지난 요약은 받아도 의미가 적다.
- **알림 통로 분리**: 사용자 요약은 카카오톡(운영), 관리자 장애 알림은 텔레그램. 카카오 토큰 만료가 장애 원인일 때 그 장애를 카카오톡으로 알리면 못 받는다.

### 3-10. 프론트엔드 개발 순서

- **결정**: 계약 우선(Contract-first). 백엔드 파이프라인 → OpenAPI 명세 → 프론트(목 데이터)와 조회 API 병행 개발 → 통합.
- **비교**: 처음부터 프론트 병행 vs 데이터 쌓인 뒤 프론트 vs 계약 우선
- **왜**:
  - 실무에서 프론트/백엔드가 협업하는 방식이 "API 명세 합의 → 동시 개발 → 통합"이다. 혼자서 두 역할을 재현한다.
  - 처음부터 프론트를 같이 만들면 초반 백엔드 구조 변경 때마다 화면도 같이 고쳐야 한다. 파이프라인이 한 번 돌아 데이터 모양이 확정된 뒤가 API 설계 적기.
  - 명세를 먼저 쓰면 "프론트가 쓰기 편한 응답 모양"을 고민하게 된다. 백엔드만 할 땐 안 하는 고민.
  - 목 데이터(MSW)로 프론트를 먼저 완성하면 백엔드 의존 없이 개발하는 법을 익힌다.
  - 통합 단계에서 CORS, 에러 응답 형식, 날짜 형식 불일치 같은 실무 문제를 직접 겪는다.
- **도구**: springdoc(OpenAPI 자동 생성, Swagger UI), MSW(프론트 목 서버), React + TypeScript.
- **미리 챙길 것**: 백엔드 조회 API는 처음부터 REST 규칙에 맞게. 예: `GET /stocks`, `GET /stocks/{ticker}/summaries`.

### 3-11. 배포 환경

- **결정**: 개발 중엔 내 PC + Docker Compose. 파이프라인이 돌기 시작하면 클라우드 VM(리눅스 서버 한 대)으로 배포.
- **비교**: 내 PC만 vs PaaS(Railway, Render, Fly.io) vs 클라우드 VM vs 쿠버네티스
- **왜**:
  - 저녁 분석, 아침 채점, 사용자별 발송 시간에 앱이 떠 있어야 하고, 요약·예측은 따라잡지 않기로 했으므로 PC를 꺼두면 그날 요약이 빠진다. 결국 클라우드가 필요.
  - PaaS는 편하지만 무료 티어가 스케줄 작업에 안 맞고(유휴 시 잠듦), 서버 내부를 안 보여줘서 배우는 게 적다.
  - 클라우드 VM은 SSH, Docker 설치, 방화벽, nginx, 재부팅 시 자동 시작, 로그 확인 등 실무에서 "배포"라 부르는 일을 직접 겪는다.
  - 쿠버네티스는 서버 한 대짜리엔 과함.
  - 로컬에서 Docker Compose로 배포 환경과 같은 구성을 먼저 만들면, Compose 파일이 시스템 구성 문서 역할도 한다.
- **VM 후보**: Oracle Cloud Always Free(ARM 4코어, 24GB, 영구 무료, 가입 까다로움) 1순위. 안 되면 Vultr 서울 리전 등 월 $5~6 VPS. AWS 프리티어는 1GB라 셋 다 띄우기 빠듯.
- **인프라 규칙**:
  - **prod는 nginx만 밖으로 연다.** 외부에 여는 포트는 nginx의 80·443과 SSH 22뿐. backend, analyzer, postgres는 Compose 내부 네트워크로만 통신한다. DB 포트가 인터넷에 열리면 봇이 몇 분 안에 찾아내 비밀번호 대입 공격을 한다.
  - **prod DB 데이터는 Docker 볼륨에.** 컨테이너는 배포 때마다 버리고 새로 만드는 일회용이라, 볼륨 없이 DB 파일을 컨테이너 안에 두면 배포할 때 데이터가 같이 사라진다.
  - **local은 postgres 5432를 PC에 연다.** DBeaver 같은 DB 클라이언트로 직접 들여다보기 위해서. 내 PC는 공유기 뒤라 인터넷에서 직접 들어올 수 없어 안전하다.
- **보류**: Llama를 내 PC GPU에서 돌리는 단계가 오면, 클라우드의 Spring Boot가 내 PC의 분석 서버를 호출하는 구조 문제를 그때 다시 결정.

## 3-B. 2차 실무 설계 결정

### B-1. Git 브랜치 전략과 커밋 규칙

- **결정**: GitHub Flow + 셀프 리뷰 PR + Conventional Commits
- **비교**: Git Flow vs GitHub Flow vs Trunk-based
- **왜**:
  - Git Flow는 `develop`, `release`, `hotfix`까지 브랜치 다섯 종류라 혼자 하는 프로젝트엔 관리만 늘어난다.
  - Trunk-based는 `main`에 바로 커밋하는 방식이라 PR과 리뷰 흐름을 연습할 기회가 없다.
  - GitHub Flow는 `main` + `feature/*` 브랜치 + PR로 단순하고, 회사에서 PR 올리고 리뷰받는 흐름과 같다.
  - 혼자여도 PR을 올리고 diff를 스스로 읽고 코멘트를 남긴 뒤 머지한다(셀프 리뷰). 코드 보는 눈을 키우는 데 효과적이고, 나중에 CI가 붙으면 "테스트 통과해야 머지" 흐름으로 이어진다.
  - Conventional Commits(`feat:`, `fix:`, `chore:`, `docs:`, `refactor:`, `test:`)는 로그만 봐도 작업 종류가 보이고, 변경 이력 자동 생성 도구와 호환된다.
- **규칙**:
  - 브랜치 이름: `feature/뉴스-수집-api`, `fix/기사-중복-저장` 형태. 영어 권장.
  - `main`에 직접 커밋 금지. 반드시 PR 경유. (첫 커밋만 예외: 브랜치를 딸 기준이 필요해서)
  - 커밋 메시지: `type: 요약` 한 줄, 필요하면 빈 줄 뒤 본문.
- **GitHub 설정** (레포 `junhwan0427/stock-news-summarizer`, 공개):
  - Ruleset `protect-main`, 대상 `main`, Active, Bypass 없음(레포 주인도 예외 없음).
  - 규칙: PR 필수(필요 승인 0, 혼자라 자기 PR을 승인할 수 없으므로), 강제 푸시 금지, 브랜치 삭제 금지.
  - "CI 통과 필수"는 CI를 만든 뒤 추가.
- **머지 방식: Squash and merge만 허용** (레포 설정에서 merge commit, rebase 끔). PR 하나가 `main`에 커밋 하나로 들어가 `main` 이력이 "PR 목록"처럼 깔끔해진다. 브랜치 안의 세부 커밋은 PR 페이지에 남는다. 비교: merge commit(이력이 정확하지만 갈래와 합침 커밋이 많아짐), rebase(합침 커밋 없이 이어 붙임).
  - PR #1은 설정 전이라 merge commit으로 들어갔다. 되돌리려면 강제 푸시가 필요한데 보호 규칙이 막으므로 그대로 둔다.
- **머지 후 브랜치 자동 삭제** 켬 (Automatically delete head branches).
- **머지 후 내 PC 정리 루틴**: `git switch main` → `git pull` → `git branch -D <작업 브랜치>`.
  - 소문자 `-d`가 아니라 대문자 `-D`인 이유: Squash 머지는 브랜치 커밋들을 새 커밋 하나로 합쳐 넣으므로, Git은 원래 커밋이 `main`에 없다고 보고 `-d`를 거절한다. GitHub에서 머지를 확인한 뒤에만 `-D`.

### B-2. 환경 분리와 설정·시크릿 관리

- **결정**: `local` / `prod` 두 프로파일. 시크릿은 환경변수로 주입. `.env`는 커밋 금지, `.env.example`에 키 이름만 커밋.
- **비교**: 환경 수(2개 vs local/dev/prod 3개), 시크릿 방식(환경변수 vs Spring Cloud Config/Vault vs 클라우드 시크릿 매니저)
- **왜**:
  - dev/staging은 배포 전 검증용 서버를 하나 더 두는 건데, 혼자 하는 프로젝트엔 과하다.
  - 설정 서버(Vault 등)는 서버 수십 대 규모용. 클라우드 시크릿 매니저는 특정 클라우드에 종속되어 Oracle/VPS와 안 맞는다.
  - 환경변수는 실무 표준이고 Docker Compose가 `.env`를 자동으로 읽는다.
- **동작 원리** (12-Factor App "설정은 환경에"):
  - jar 안에는 `${POLYGON_API_KEY}` 같은 빈칸만 있다. local과 prod의 jar는 완전히 같은 파일.
  - 값은 **실행 시점**에 환경변수에서 채워진다. 빌드 시점이 아니다.
  - 서버의 `.env`는 SSH로 한 번 직접 만들어둔다. 키를 바꾸려면 서버 `.env` 수정 후 앱 재시작. 빌드·배포 불필요.
- **규칙**:
  - Spring: `application.yml`(공통) + `application-local.yml` + `application-prod.yml`. 프로파일 파일에도 시크릿을 직접 쓰지 않고 `${...}` 참조만.
  - FastAPI: `.env.local` / `.env.prod`를 같은 원리로.
  - Spring local 실행 시 `.env` 읽기: `application-local.yml`의 `spring.config.import: optional:file:../.env[.properties]`. IntelliJ나 `gradlew bootRun`으로 실행할 때 환경변수를 따로 넣지 않아도 루트 `.env`를 읽는다. prod는 이 설정이 없고 Compose가 넣어주는 환경변수만 쓴다.
  - 프로파일을 지정하지 않으면 `local`(`spring.profiles.default`). prod는 `SPRING_PROFILES_ACTIVE=prod`.
  - `.gitignore`는 **첫 커밋 전에** 만든다. 한 번 커밋된 시크릿은 히스토리에 남으므로 키 재발급이 필요하다.
  - local은 스케줄 끄고 수동 API로만 실행, 알림은 텔레그램. prod는 스케줄 켜고 사용자 요약은 카카오톡, 장애 알림은 텔레그램.

### B-3. 프로젝트 구조

- **결정**: 모노레포 + Spring Boot는 도메인별 패키지 + 외부 연동은 포트/어댑터(interface)로 분리
- **비교**: 멀티 레포 vs 모노레포 / 레이어드 vs 도메인별 vs 헥사고날 전체 적용
- **왜**:
  - 혼자 하는 프로젝트라 레포 세 개를 오가는 것보다 한 곳에 문서·Compose·코드가 있는 게 낫다. PR 하나로 백엔드와 프론트를 같이 바꿀 수 있다.
  - 레이어드(`controller/service/repository`)는 익숙하지만 커지면 `service`에 파일이 쌓여 찾기 어렵다. 도메인별은 "요약 관련은 전부 `summary/`"라 찾기 쉽고 떼어내기도 쉽다. 도메인 경계를 긋는 고민 자체가 설계 연습.
  - 헥사고날 전체 적용은 DB 접근까지 포트로 감싸 파일이 두 배가 된다. 지금 단계엔 헤매는 비용이 더 크다. 핵심 아이디어(핵심 로직이 바깥세상을 직접 모르게)를 효과가 가장 큰 외부 연동에만 적용한다.

### B-4. 에러 처리와 응답 형식

- **결정**:
  1. 성공 응답은 감싸지 않고 데이터만. 성공 여부는 HTTP 상태 코드로.
  2. 에러 응답은 RFC 7807 Problem Details 표준 (Spring Boot 3 내장 `ProblemDetail`).
  3. 예외는 `@RestControllerAdvice` 전역 핸들러 한 곳에서 처리. 예외 클래스는 `StockNotFoundException`처럼 의미 있는 이름으로 `common/exception/`에.
  4. 외부 API 실패는 재시도 3회(간격 1→2→4초, Resilience4j) → 실패 시 `job_runs`에 FAILED 기록하고 다음 종목 진행 → 관리자에게 텔레그램으로 장애 알림.
- **비교**: 성공 응답 감싸기(`{success, data, message}`) vs 안 감싸기 / 에러 형식 자체 정의 vs RFC 7807 / 컨트롤러별 try-catch vs 전역 핸들러
- **왜**:
  - 감싸면 상태 코드와 `success` 필드가 중복이고, 프론트가 매번 한 겹 벗겨야 하며 OpenAPI 명세가 지저분해진다.
  - RFC 7807은 이미 있는 표준이라 "왜 이 형식이냐"를 설명할 필요가 없고 Spring Boot 3에 내장되어 설정 한 줄로 켜진다.
  - 컨트롤러별 try-catch는 API 수만큼 반복되고 형식 변경 시 전부 고쳐야 한다. 전역 핸들러는 고객센터 하나로 몰아 받는 것.
  - 외부 API 실패는 우리가 고칠 수 없으므로 잠깐의 장애는 재시도로 넘기고, 종목 하나 실패가 나머지를 멈추면 안 되며, 조용히 실패하는 게 가장 위험하므로 알림이 필수.

### B-5. 로깅 전략

- **결정**:
  1. 레벨 기준: ERROR(사람이 봐야 하는 실패) / WARN(실패는 아닌데 이상함) / INFO(정상 흐름 이정표) / DEBUG(개발용 상세). local은 DEBUG까지, prod는 INFO 이상.
  2. 출력은 stdout만. 파일 저장·용량 제한·순환은 Docker가 담당 (`docker compose logs`).
  3. MDC로 작업 ID(`job=daily_analysis-20260924`)와 종목(`ticker=AAPL`)을 모든 로그에 자동 부착.
  4. API 키, 토큰, 비밀번호는 절대 로그에 남기지 않음. 외부 요청 URL 로그는 키 부분 마스킹.
  5. 형식은 일반 텍스트. 로그 수집 도구(Loki, ELK) 붙일 때 JSON으로 전환.
- **비교**: 파일 직접 쓰기 vs stdout / 텍스트 vs JSON
- **왜**:
  - 밤에 혼자 도는 시스템이라 아침에 "왜 안 왔지"를 알아낼 유일한 단서가 로그. 레벨과 꼬리표 없이는 못 찾는다.
  - 파일 직접 쓰기는 위치·용량·순환을 앱이 관리해야 한다. stdout은 12-Factor "로그는 흐름"이고 컨테이너 표준. 앱에서 로그 파일 관리 코드가 사라진다.
  - 서버 한 대에선 `grep`이면 충분하므로 JSON은 수집 도구 도입 시점으로 미룬다.
- **예시**:

```
2026-09-24 20:00:03 INFO  [job=daily_analysis-20260924] [ticker=AAPL] 뉴스 12건 수집
2026-09-24 20:00:05 ERROR [job=daily_analysis-20260924] [ticker=TSLA] Polygon 타임아웃 (3/3)
```

### B-6. 테스트 전략

- **결정**:
  1. 집중 대상: 채점 로직, 따라잡기 날짜 계산, 휴장일 판단, 멱등 체크 같은 순수 로직 → 단위 테스트 꼼꼼히. Repository 쿼리, 전역 예외 핸들러 → 통합 테스트. 컨트롤러 단순 위임 → 안 짬. E2E → 안 함.
  2. 외부 API: 단위 테스트는 포트(interface)에 Mockito 가짜 구현체. 어댑터 파싱 검증은 WireMock으로 가짜 서버 띄우고 저장된 응답 JSON 재생.
  3. 통합 테스트 DB: Testcontainers로 진짜 PostgreSQL을 Docker로 잠깐 띄움.
  4. 스타일: 메서드명은 "상황_결과" 한글 허용, 본문은 given / when / then.
- **비교**: H2 인메모리 vs Testcontainers / 전부 테스트 vs 우선순위
- **왜**:
  - "전부 테스트"는 지쳐서 하나도 안 짜게 된다. 틀리면 적중률 통계가 전부 틀리는 순수 로직에 집중.
  - 진짜 Polygon/Claude를 테스트마다 부르면 느리고 돈 들고 인터넷 끊기면 실패. 포트/어댑터로 나눈 이유가 여기서 살아난다.
  - H2는 PostgreSQL이 아니라 JSONB 등이 달라 "테스트는 되는데 진짜 DB에선 안 됨"이 생긴다. Docker는 어차피 있으니 Testcontainers.
  - 테스트 이름이 곧 문서.

### B-7. CI

- **결정**:
  1. 도구: GitHub Actions.
  2. 시점: PR 생성·업데이트 시, `main` 머지 시.
  3. 범위: 모노레포라 바뀐 폴더만 실행. `backend/` → Gradle 빌드+테스트(Testcontainers용 Docker는 Actions 기본 제공). `analyzer/` → 린트+테스트. `frontend/` → 타입 체크+린트+빌드.
  4. 머지 규칙: `main` 브랜치 보호 규칙으로 "CI 통과 필수".
  5. CD(자동 배포)는 지금 안 함. SSH로 수동 배포를 몇 번 겪은 뒤 자동화.
- **구현** (`.github/workflows/backend-ci.yml`):
  - 워크플로는 **모든 PR에서 실행**하되, 첫 작업(`changes`)이 `dorny/paths-filter`로 `backend/`가 바뀌었는지 보고, 안 바뀌었으면 빌드 작업(`backend-build`)을 건너뛴다(Skipped).
  - 왜 `on.pull_request.paths`로 거르지 않나: 그러면 문서만 바꾼 PR에선 워크플로 자체가 안 돌고, "CI 통과 필수"로 걸어둔 체크가 영원히 "대기 중"이 되어 머지가 막힌다. 건너뛴(Skipped) 작업은 통과로 인정된다.
  - 권한은 최소로(`contents: read`, `pull-requests: read`). 같은 PR에 연달아 푸시하면 이전 실행은 취소(`concurrency`).
  - 보호 규칙의 필수 체크 이름: `backend-build`.
  - `analyzer/`, `frontend/`가 생기면 같은 방식으로 워크플로를 하나씩 추가한다.
- **비교**: GitHub Actions vs Jenkins vs GitLab CI / CD 지금 vs 나중
- **왜**:
  - CI는 "코드 올릴 때마다 자동으로 빌드·테스트하는 로봇". 혼자여도 "내 PC에선 됐는데"를 막고 테스트를 강제로 돌리게 한다.
  - Jenkins는 서버를 직접 관리해야 해 혼자 하기엔 부담. GitHub Actions는 YAML 하나로 끝, 실무 표준.
  - 백엔드 한 줄 고쳤는데 프론트까지 빌드하면 낭비.
  - CD는 서버도 없는 지금 할 이유가 없고, 수동 배포를 몸으로 익힌 뒤 자동화해야 왜 필요한지 안다.

### B-8. DB 마이그레이션 도구

- **결정**: Flyway. `spring.jpa.hibernate.ddl-auto=validate`. 머지된 마이그레이션 파일은 수정 금지, 변경은 새 번호로.
- **비교**: JPA `ddl-auto=update` vs Flyway vs Liquibase
- **왜**:
  - 마이그레이션은 테이블 구조 변경 이력을 번호 붙인 파일로 관리하는 것. 로컬과 서버 DB 구조를 항상 같게 유지한다.
  - `ddl-auto=update`는 기록이 안 남고, 컬럼 이름 변경 시 옛 컬럼을 방치한다. prod에서 켜는 건 금기.
  - Liquibase는 XML/YAML 문법을 새로 배워야 하고 DB 독립성은 PostgreSQL 하나만 쓰는 우리에겐 불필요.
  - Flyway는 그냥 SQL이라 "이 테이블이 왜 이렇게 생겼는지"를 이해하기 가장 좋다.
- **규칙**:
  - 파일명: `V1__create_stocks.sql`, `V2__create_articles.sql` 형식. 파일 하나에 변경 하나.
  - `validate`로 두면 Entity와 실제 테이블이 안 맞을 때 앱이 뜨지 않아 즉시 잡힌다.
  - 이미 서버에 적용된 파일을 고치면 로컬과 서버가 갈라지므로 절대 수정하지 않는다.

### B-9. 회원제 여부

- **결정**: C안. 테이블은 처음부터 회원제로 설계(`users`, `user_stocks`), 인증은 파이프라인 완성 후에 붙인다. 초기엔 사용자가 나 하나.
- **비교**: A. 나 혼자용으로 끝 / B. 처음부터 회원제 + 인증 / C. 테이블만 회원제, 인증은 나중
- **왜**:
  - 테이블 구조는 데이터가 쌓인 뒤 바꾸기가 가장 아프다. "모든 예측에 사용자 개념 추가"를 나중에 하면 마이그레이션이 복잡해진다.
  - 인증은 나중에 붙여도 기존 데이터에 영향이 없다.
  - B는 인증 붙이다 지쳐서 파이프라인이 돌기 전에 멈출 위험.
- **회원제로 바뀌는 것**:
  - 요약·예측은 종목당 한 번만 만들고, 그 종목을 보는 모든 사용자에게 공유. 사용자별로 만들면 Claude 비용이 사용자 수만큼 는다.
  - 알림은 사용자별(받을 종목, 받을 시간). 카카오 로그인을 회원가입 수단으로 쓰면 로그인과 "나에게 보내기" 권한이 한 번에 해결된다.
  - 조회 API는 "로그인한 사용자의 것만" 필터가 붙는다.
  - 사용자당 관심 종목 수 제한 등 비용 통제 규칙 필요.

### B-10. 종목 관리 구현 결정 (2026-09-27)

- **인증 전 "지금 사용자"**: 고정 사용자. V4 마이그레이션으로 관리자 1명(`admin@stocknews.local`)을 넣고, `CurrentUserProvider` 포트의 `FixedCurrentUserProvider`가 항상 그 사용자를 돌려준다. 인증을 붙이면 이 구현체만 로그인 정보를 읽는 것으로 교체.
  - 비교: 요청 헤더 `X-User-Id`로 받기. 아무나 남의 ID를 넣을 수 있는 구조라 나쁜 습관이 들고, 인증 때 고칠 곳이 많다.
- **API 주소**: `/me/stocks` (`GET` 목록, `POST` 추가, `DELETE /{ticker}` 해제).
  - `/me`는 인증 후에도 그대로 쓰는 표준. 누구인지를 주소가 아니라 서버가 정해서, 주소의 ID를 바꿔 남의 데이터를 보는 사고가 구조적으로 막힌다. 남의 데이터가 필요한 관리자 기능은 `/admin/users/{id}/...`로 따로 만든다.
- **HTTP 클라이언트**: `RestClient`. 비교: WebClient(비동기, 추가 라이브러리 필요), RestTemplate(구식), OpenFeign(Spring Cloud 필요).
  - Massive 키는 URL(`?apiKey=`)이 아니라 `Authorization: Bearer` 헤더로 보낸다. URL은 로그·에러 메시지에 찍히기 쉽다(B-5).
  - 연결 5초, 읽기 10초 타임아웃.
  - 재시도(Resilience4j)는 배치 작업(뉴스 수집)을 만들 때 붙인다. 사용자 요청은 실패를 바로 알려주는 게 낫다.
- **Lombok** 추가. Entity는 `@Getter` + `@NoArgsConstructor(access = PROTECTED)`, 서비스는 `@RequiredArgsConstructor`. `@Setter`는 쓰지 않고 의미 있는 메서드(`delete()`, `restore()`, `activate()`)로만 상태를 바꾼다.
- **응답 코드**:

| 상황 | 코드 | title |
|---|---|---|
| 추가 성공 | 201 | |
| 목록 | 200 | |
| 해제 성공 | 204 | |
| 입력 형식 오류 (`@Valid`) | 400 | 입력값 오류 (`errors`에 필드별 메시지) |
| 확인되지 않는 티커 | 400 | 존재하지 않는 종목 |
| 이미 관심 종목 | 409 | 이미 관심 종목 |
| 개수 제한 초과 | 409 | 관심 종목 수 초과 |
| 관심 종목 아닌데 해제 | 404 | 관심 종목이 아님 |
| Massive 실패 | 502 | Massive API 오류 |

- **티커 검증**: 형식은 `@Pattern`(영문자로 시작, 영문자·점 최대 10자, 예: `BRK.B`). 존재 여부는 Massive `GET /v3/reference/tickers/{ticker}`로 `market=stocks`, `locale=us`, `active=true`인지 확인. DB에 이미 있는 종목이면 외부 호출을 하지 않는다.
- **명명**: 서비스가 Polygon에서 Massive로 이름을 바꿔 어댑터 이름은 `Massive...`. 환경변수는 이미 쓰고 있는 `POLYGON_API_KEY` 유지.

## 4. 데이터 모델

```
users ──┬── user_stocks ──── stocks ──┬── stock_articles ── articles
        │                             ├── summaries ──┬── summary_articles ── articles
        │                             │               └── predictions ── prediction_results
        │                             └── daily_prices
        └── notification_logs
job_runs (독립)
```

요약이 주인공. LLM 호출 한 번으로 요약(핵심 기사 + 요약 문단)과 예측이 함께 나오며, 예측은 요약을 가리킨다.

공통 규칙:
- 시각은 전부 `timestamptz`, UTC 저장. 표시할 때만 KST 변환.
- PK는 `bigint`, `GENERATED AS IDENTITY`.
- 소프트 삭제 대상(`deleted_at` 컬럼): `users`, `stocks`, `user_stocks`.
- 삭제 없음(쌓기만): `articles`, `stock_articles`, `summaries`, `summary_articles`, `predictions`, `prediction_results`, `daily_prices`, `job_runs`, `notification_logs`. 학습 데이터와 이력.

### 4-1. `users` — 확정

| 컬럼 | 타입 | 설명 |
|---|---|---|
| id | bigint PK | |

| nickname | varchar(50) | |

### 4-3. `user_stocks` — 확정

| 컬럼 | 타입 | 설명 |
|---|---|---|
| user_id | FK → users | |
| stock_id | FK → stocks | |
| notify | boolean | 이 종목 알림 받을지 |
| created_at | timestamptz | |
| deleted_at | timestamptz null | 소프트 삭제 |

PK: `(user_id, stock_id)`.
- 해제했다가 다시 추가하면 같은 행을 되살린다(`deleted_at = null`, `created_at = 지금`). PK가 (사용자, 종목)이라 같은 조합의 행은 하나뿐이어서, "마지막으로 해제한 시각"까지만 남고 여러 번 넣었다 뺀 전체 이력은 남지 않는다. 전체 이력이 필요해지면 별도 id + 부분 유니크 인덱스로 바꾼다(미결).

제한 규칙 (설정값, 코드에 박지 않음):
- 사용자당 최대 종목 수: USER 5개(기본값), ADMIN 무제한.
- 시스템 전체 활성 종목 상한: 설정값으로만 두고 처음엔 넉넉히. 사용자가 늘 때 조정.

### 4-4. `articles` — 확정

| 컬럼 | 타입 | 설명 |
|---|---|---|
| id | bigint PK | |
| url | text unique | 중복 방지 기준 |
| title | text | |
| description | text | API가 주는 짧은 설명 |
| source | varchar(100) | 매체명 |
| published_at | timestamptz | |
| provider | varchar(20) | POLYGON / FINNHUB |
| raw | jsonb | **API 응답 JSON 통째로** (Polygon insights 포함, 학습 라벨용) |
| created_at | timestamptz | |

용어 구분:
- `raw` = API 응답 JSON. 기사 본문은 여기 없다(API가 안 줌).
- `content` = 기사 본문. **지금은 안 넣는다.** Llama 학습 직전에 크롤링(trafilatura)을 붙이고 `content` 컬럼을 마이그레이션으로 추가, 과거 기사도 소급. 실패 시 null.

### 4-6. `summaries` — 확정 (주인공)

| 컬럼 | 타입 | 설명 |
|---|---|---|
| id | bigint PK | |
| stock_id | FK → stocks | |
| target_date | date | 대상 거래일 (미국 날짜 = 생성한 날의 KST 날짜) |
| body | text | 요약 문단 |
| model_name | varchar(50) | claude-opus-5, llama-ft-v1 등 |
| prompt_version | varchar(20) | 프롬프트 바뀔 때마다 올림 |
| raw_response | jsonb | LLM 응답 JSON 통째로 (요약 + 예측 모두 포함) |
| created_at | timestamptz | 다음 뉴스 수집 범위("마지막 요약 이후")의 기준 |

유니크 `(stock_id, target_date)` = **멱등의 기준.** 같은 날 두 번 돌려도 두 번째는 못 들어간다.
컬럼 이름을 `summary`가 아니라 `body`로 한 이유: `summaries.summary`는 읽을 때 헷갈린다.

### 4-7. `summary_articles` — 확정 (핵심 기사 연결)

| 컬럼 | 타입 |
|---|---|
| summary_id | FK → summaries |
| article_id | FK → articles |
| rank | smallint |

PK `(summary_id, article_id)`. 배열 컬럼 대신 연결 테이블: 외래키가 걸리고 "이 기사가 근거로 쓰인 요약들"을 역조회할 수 있다.

### 4-7b. `predictions` — 확정 (실험)

| 컬럼 | 타입 | 설명 |
|---|---|---|
| id | bigint PK | |
| summary_id | FK → summaries, unique | 어떤 요약에서 나온 예측인지. 요약당 최대 하나 |
| direction | varchar(10) | UP / DOWN / NEUTRAL |
| confidence | numeric(3,2) | 0.00 ~ 1.00 |
| reasoning | text | 판단 근거 |
| created_at | timestamptz | |

- `stock_id`, `target_date`, `model_name`, `raw_response`는 `summary_id`를 따라가서 본다. 중복 저장 안 함.
- 요약만 켜고 예측은 끄는 구성이 자연스럽다(설정값).
- **왜 예측 테이블에 요약 컬럼을 넣지 않고 따로 두나**: 구조가 목표를 말해야 한다. "요약 보려면 predictions 테이블"은 이름이 어긋나고, 예측을 끄고 싶을 때 꼬인다.

### 4-8. `prediction_results` — 확정 (채점)

| 컬럼 | 타입 | 설명 |
|---|---|---|
| prediction_id | FK → predictions, PK | 예측당 결과 하나 |
| open_price | numeric(12,4) | |
| close_price | numeric(12,4) | |
| change_pct | numeric(6,3) | (close - open) / open × 100 |
| actual_direction | varchar(10) | 실제 UP / DOWN / NEUTRAL |
| hit | boolean | 예측 = 실제 |
| scored_at | timestamptz | |

규칙:
- 예측 테이블과 분리하는 이유: 생성 시점이 다르고, "채점 안 된 예측"이 자연스럽게 표현되며, 채점 기준을 바꿔 재채점할 때 결과만 다시 만들면 된다.
- 채점 기준: **당일 시가 → 당일 종가.** 예측을 장 열리기 전에 하므로 밤새 갭은 시가에 이미 반영. 전날 종가 기준보다 정직하다.
- NEUTRAL 기준: 등락률 절댓값 < 0.5% (설정값).

| 컬럼 | 타입 |
|---|---|
| id | bigint PK |
| stock_id | FK → stocks |
| trade_date | date |
| open / high / low / close | numeric(12,4) |
| volume | bigint |
| created_at | timestamptz |

유니크 `(stock_id, trade_date)`. 백필과 매일 적재 모두 여기. 채점은 여기서 읽는다.

### 4-10. `job_runs` — 확정

| 컬럼 | 타입 | 설명 |
|---|---|---|
| id | bigint PK | |
| job_name | varchar(50) | DAILY_ANALYSIS / SCORE / COLLECT / BACKFILL (발송 작업은 기록 안 함) |
| target_date | date | |
| status | varchar(20) | RUNNING / SUCCESS / FAILED / SKIPPED |
| started_at, finished_at | timestamptz | |
| stats | jsonb | 성공/실패 수, 실패 종목 목록, 건너뛴 이유(휴장 등) |
| error_message | text | |

- 시도마다 새 행. "3번 실패 후 4번째 성공" 이력이 남아야 장애 분석이 된다.
- 따라잡기는 "그 날짜에 SUCCESS 또는 SKIPPED 행이 있나"만 본다. 휴장일을 매번 다시 시도하지 않게 SKIPPED도 "처리 끝남"으로 친다.

### 4-10b. `notification_logs` — 확정 (발송 기록)

| 컬럼 | 타입 | 설명 |
|---|---|---|
| id | bigint PK | |
| user_id | FK → users | |
| notify_date | date | 발송 날짜 (KST). "하루 한 번"의 기준 |
| channel | varchar(20) | KAKAO / TELEGRAM |
| status | varchar(20) | SUCCESS / FAILED |
| error_message | text null | 실패 이유 |
| created_at | timestamptz | 시도 시각 |

- 시도마다 새 행. 실패는 여러 번 남고, 다음 30분에 재시도된다.
- **부분 유니크 인덱스** `(user_id, notify_date) WHERE status = 'SUCCESS'`: 성공한 발송만 하루 하나로 제한한다. 전체에 유니크를 걸면 실패 후 재시도가 막힌다.
- 이름을 `target_date`가 아니라 `notify_date`로 한 이유: 요약의 `target_date`(미국 거래일)와 헷갈리지 않게.

### 4-11. 인덱스 — 확정

자동 생성(유니크 제약):

| 테이블 | 컬럼 | 용도 |
|---|---|---|
| users | email | 로그인 조회 |
| stocks | ticker | 티커 조회, 중복 방지 |
| articles | url | 기사 중복 방지 |
| summaries | (stock_id, target_date) | 멱등 체크 |
| predictions | summary_id | 요약당 예측 하나 |
| daily_prices | (stock_id, trade_date) | 중복 방지, 채점 시 가격 조회 |

직접 생성:

| 테이블 | 컬럼 | 왜 |
|---|---|---|
| articles | (published_at) | "마지막 요약 이후 기사" 조회 |
| stock_articles | (article_id) | 기사 → 종목 역조회 (PK 순서상 article_id 단독 검색 불가) |
| summaries | (target_date) | "그날 요약 전부" 조회, 발송 |
| user_stocks | (stock_id) WHERE deleted_at IS NULL | 종목별 활성 사용자 수. 부분 인덱스 |
| job_runs | (job_name, target_date, status) | 따라잡기의 "그 날짜 처리 끝났나" |
| notification_logs | (user_id, notify_date) WHERE status = 'SUCCESS', **유니크** | 하루 한 번 성공 보장 + "오늘 받았나" 조회 |

일부러 안 거는 것:
- `prediction_results`: PK로 충분. 적중률 통계는 전체 스캔이라 인덱스 무의미.
- JSONB 컬럼: 지금은 JSON 안을 검색할 일 없음. 필요 시 GIN 인덱스.
- `users.notify_time`: 사용자 수가 적어 30분마다 전체를 훑어도 충분. 사용자가 늘면 추가.

> **ERD 확정 (2026-09-24).** 이후 변경은 Flyway 마이그레이션 파일과 이 문서를 함께 갱신한다.

### 4-12. 나중에 추가할 것 (사용자 승인됨, 시점은 미정)

하루 방향 예측은 잡음이 커서 의미가 약할 수 있다. 의미를 키우는 장치들. `daily_prices`가 매일 쌓이므로 나중에 붙여도 소급 채점 가능.
- **다기간 채점**: `prediction_results`에 `horizon_days` 추가, PK를 `(prediction_id, horizon_days)`로. 1일/3일/5일 결과를 각각.
- **시장 대비 채점**: SPY를 시스템 종목으로 수집, `market_change_pct`와 `relative_hit` 추가.
- **기준선 비교**: "항상 UP" 같은 바보 예측기의 적중률을 같이 계산.
- **뉴스 종류별 적중률**: Claude가 붙인 분류 라벨 기준.
