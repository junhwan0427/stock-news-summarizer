# 질문 정리

> 프로젝트 진행 중에 물어본 것들과 답을 모아둔다. 나중에 다시 헷갈릴 때 보는 용도.

---

## SDK가 뭔가요?

API는 "이렇게 요청하면 이렇게 답해줄게"라는 약속이다. 그 약속대로 직접 하려면 주소, 인증 헤더, JSON 만들기, 응답 파싱을 내가 다 짜야 한다.
SDK는 그 귀찮은 걸 제공사가 미리 짜서 라이브러리로 준 것. API가 메뉴판이면 SDK는 배달앱.
`RestTemplate`/`WebClient`로 직접 호출해도 되고, SDK를 쓰면 코드가 짧아질 뿐이다.

## LLM이면 파이썬을 써야 하나요?

아니다. 파이썬이 AI에 강한 건 모델을 **학습**시킬 때 얘기다. 이미 만들어진 모델을 **API로 호출**하는 건 HTTP 요청이라 어떤 언어든 된다.
파이썬이 진짜 필요해지는 시점은 Llama를 직접 파인튜닝할 때다.

## LLM을 "학습"시킨다는 게 뭔가요?

LLM을 신입사원에 비유하면:
- **사전학습(Pretraining)**: 태어나서 대학 졸업까지 받은 교육. Meta가 이미 시켜서 Llama로 공개. 개인은 불가능.
- **파인튜닝(Fine-tuning)**: 우리 회사에 입사시켜 우리 일을 가르치는 것. "이런 뉴스 → 주가 이렇게 움직임" 예시 수백 개를 보여준다. 개인도 가능. LoRA 기법을 쓰면 GPU 한 장으로도 된다.
- **RAG**: 가르치진 않고, 일 시킬 때마다 참고 자료를 옆에 놓아주는 것. 모델은 그대로.

파인튜닝엔 "교재"(입력 → 정답 쌍)가 최소 수백 건 필요하다. 교재는 "그날 뉴스 → 다음 날 실제 주가"로 만들 수 있고, Claude 예측은 필요 없다. 정답은 실제 주가가 알려준다.

## "처음엔 Claude API로 시작"이 무슨 뜻인가요?

프로그램이 매일 돌려면 "뉴스 읽고 판단하는 두뇌"가 필요한데, 최종 두뇌인 "내가 가르친 Llama"는 아직 없다.
그래서 그 자리를 당분간 Claude로 채운다는 뜻. 나중에 두뇌만 Llama로 갈아끼우고 나머지는 그대로 둔다. 그래서 두뇌 부분을 `interface`로 분리한다.

## 과거 데이터로 미리 예측시켜서 데이터를 쌓으면 안 되나요?

교재는 쌓을 수 있다(백테스트). 하지만 Claude로 과거를 "예측"시켜 적중률을 재는 건 의미가 없다.
Claude는 2024년 뉴스를 보면 그 뒤 일어난 일을 이미 알고 있기 때문. 시험 답을 미리 본 학생에게 시험 보게 하는 것과 같다. 이걸 **데이터 누수(data leakage)**라고 한다.
그래서 과거 데이터는 교재용으로만 쓰고, Claude의 진짜 성적은 오늘부터 앞으로 쌓이는 것으로만 잰다.

## 전부 무료로 할 수 있나요?

Claude API만 유료(월 약 $6, 선불 충전)이고 나머지는 전부 무료. Claude API는 무료 티어가 없다.
과거 데이터 백필은 뉴스/주가 API만 쓰므로 Claude 비용 0원.

## PostgreSQL도 무료인가요?

완전 무료(오픈소스). 돈이 드는 건 클라우드에서 DB 서버를 빌릴 때뿐이고, 그것도 Supabase/Neon 같은 곳은 무료 티어가 있다.

## 관계형 DB와 NoSQL 차이는?

- **관계형 DB(MySQL, PostgreSQL)**: 엑셀 시트 여러 장. 각 행에 ID가 있고, ID로 시트끼리 연결(조인)한다. "모든 종목의 틀린 예측만 모아줘" 같은 가로지르는 질문에 강하다.
- **NoSQL(MongoDB)**: 서류철. 문서 하나에 관련 정보를 통째로 넣는다. 한 문서만 보면 되는 경우엔 편하지만, 문서를 가로질러 찾는 건 약하다.

우리 데이터는 가로지르는 질문이 대부분이라 관계형 DB.

## MySQL vs PostgreSQL vs SQLite

- **SQLite**: 파일 하나가 DB. 제일 쉽지만 서버 두 개가 동시에 쓰기엔 부적합.
- **MySQL**: 가장 널리 쓰임. JSON 저장은 되지만 JSON 안의 값으로 검색/인덱스가 불편.
- **PostgreSQL**: JSONB로 JSON을 넣고 검색/인덱스까지 가능. 배열, 전문 검색 기본 제공. 파이썬 분석 도구와 궁합 좋음.

둘 다 SQL 문법이 거의 같아서 하나 배우면 다른 것도 금방 쓴다.

## 시퀀스가 뭔가요?

"번호표 뽑는 기계". 새 행에 겹치지 않는 고유 번호(기본키, Primary Key)를 자동으로 붙여준다.
- MySQL은 컬럼에 `AUTO_INCREMENT`를 붙인다. 번호표 기계가 테이블에 붙어 있는 느낌.
- PostgreSQL은 시퀀스가 테이블과 별개의 독립 객체. 그래서 "시퀀스를 건다" = "이 컬럼이 저 시퀀스에서 번호를 뽑게 연결한다". 요즘은 `GENERATED AS IDENTITY`로 자동 처리.
- Spring Boot에선 `@GeneratedValue(strategy = GenerationType.IDENTITY)` 한 줄이면 둘 다 동일.

## 조회가 느릴 때 "시퀀스를 건다"?

아마 "인덱스를 건다"를 잘못 들은 것. 둘은 완전히 다르다.
- **시퀀스** = 번호표 기계. ID 발급. 속도와 무관.
- **인덱스** = 책 뒤의 색인. 검색 속도를 높인다.

인덱스가 없으면 DB가 모든 행을 처음부터 끝까지 읽는다(풀스캔). 인덱스가 있으면 미리 정렬된 자료구조에서 바로 짚고 점프한다.
공짜는 아니다: 새 행이 들어올 때마다 색인도 갱신해야 해서 **조회는 빨라지고 쓰기는 조금 느려진다.** 자주 검색 조건으로 쓰는 컬럼에만 건다.

```sql
CREATE INDEX idx_articles_stock_date ON articles (stock_id, published_at);
```

느린 쿼리 확인법: 쿼리 앞에 `EXPLAIN ANALYZE`를 붙이면 풀스캔 했는지 인덱스 썼는지 보여준다.

## 앱을 안 켜놨다가 다시 켰을 때 밀린 작업이 돌게 하려면 Quartz가 필요한가요?

아니다. `job_runs` 테이블에 "마지막으로 성공한 날짜"를 기록해두고, 앱 시작 시 그 다음 날부터 오늘까지 빠진 날짜를 계산해서 순서대로 돌리면 된다. 20~30줄짜리 로직.
Quartz는 이걸 **미스파이어(misfire) 처리**라는 이름으로 내장한 것. 작업이 수십 개가 되거나, 서버가 두 대 이상이거나, 스케줄을 DB에서 바꾸고 싶을 때 넘어가면 된다.

단, **예측은 따라잡으면 안 된다.** 3일 뒤에 3일 전 예측을 만들면 그 사이 뉴스에 이미 결과가 섞여 있어서 데이터 누수가 생긴다. 채점과 데이터 수집만 따라잡는다.

**결론: 이 프로젝트에선 Quartz를 넣을 필요가 없다.** `@Scheduled` + `job_runs` + 시작 시 따라잡기로 충분.

## 벡터 DB는 결정 안 해도 되나요?

문장을 숫자 묶음(임베딩)으로 바꾸면 의미가 비슷한 문장은 숫자도 비슷해진다. **벡터 DB**는 그 숫자 묶음을 저장하고 "이거랑 제일 비슷한 것"을 빠르게 찾아주는 DB. 일반 검색은 "단어 포함 여부", 벡터 검색은 "의미 유사도".

이 프로젝트에서 쓸 자리: "오늘 뉴스와 비슷한 과거 뉴스 때 주가가 어떻게 됐나"를 찾아 Claude에 같이 보내기(RAG).

**결론: 지금은 안 씀.** 나중에 필요해지면 PostgreSQL에 **pgvector** 확장을 붙이면 되므로 별도 벡터 DB를 띄울 필요가 없다. PostgreSQL을 고른 이유가 하나 더 생긴 셈.

## 알림을 카카오톡으로 할 수 있나요?

가능하지만 텔레그램보다 훨씬 번거롭다.
- 카카오 개발자 앱 등록 + 로그인 연동 + "나에게 보내기" 권한 필요.
- 액세스 토큰이 몇 시간마다 만료되어 리프레시 토큰으로 자동 갱신하는 로직이 필요. 안 하면 알림이 조용히 끊긴다.
- 보낼 수 있는 대상은 나 자신뿐. 메시지도 정해진 템플릿 안에서만.
- 남에게 보내는 알림톡은 사업자 등록 필요.

텔레그램은 봇 토큰 하나면 만료 없이 HTTP 요청 한 번으로 끝. 알림을 `interface`로 분리해두고 카카오톡은 2차 목표로. 토큰 갱신 로직은 OAuth 연습으로 괜찮다.

## TS를 굳이 왜 쓰나요? JS 쓰면 안 되나요?

TS = JS + 타입. Java의 `String name`, `int count`처럼 "이 변수는 뭐다"를 적는 것. 실행은 결국 JS로 변환되어 돌아간다.

- **JS**: 배울 게 적고 코드가 짧다. 대신 오타, 없는 필드 접근, 타입 불일치 같은 실수를 **실행해봐야** 안다. `prediction.confidence`인데 실제 필드가 `confidenceScore`면 조용히 `undefined`.
- **TS**: 그 실수를 **코드 쓰는 순간** 에디터가 빨간 줄로 알려준다. 자동완성이 정확해진다. 대신 타입 정의로 코드가 길어지고 빌드 단계가 하나 생긴다.

이 프로젝트에서 특히 맞는 이유: 계약 우선 개발이라 OpenAPI 명세에서 TS 타입을 자동 생성할 수 있다. 백엔드가 응답 모양을 바꾸면 프론트에서 안 맞는 곳이 전부 빨간 줄로 뜬다.
비유: JS는 메모장, TS는 맞춤법 검사 켠 에디터. 긴 글일수록 차이가 커진다.

## TanStack Query(React Query)가 뭔가요?

같은 라이브러리. React 전용이었다가 다른 프레임워크도 지원하면서 TanStack Query로 개명.
"서버에서 데이터 가져오는 일"을 대신 관리한다: API 호출, 로딩/에러 상태, 캐시, 오래된 데이터 재요청을 `useQuery` 한 줄로. 실무 React에서 API 붙일 때 사실상 표준.

## Redux는 store 같은 건가요?

맞다. 앱 전체가 공유하는 상태를 한 곳(store)에 모으고 정해진 방식으로만 바꾸는 라이브러리.
- **TanStack Query**: 서버에서 온 데이터(예측 목록, 종목 목록).
- **Redux / Zustand**: 화면 자체의 상태(선택된 탭, 다크모드).

예전엔 서버 데이터도 Redux에 넣었지만 캐시·재요청을 손으로 짜야 해서, 요즘은 TanStack Query에 넘기고 Redux 역할이 줄었다. 남은 화면 상태는 가벼운 Zustand나 아예 안 씀.

## Node.js는 쓰나요?

쓰지만 **서버로 쓰지 않는다.** 서버는 Spring Boot. Node.js는 Vite 개발 서버, TS 변환·번들링, ESLint/Prettier, npm 설치 같은 **개발 도구를 돌리는 용도**.
Java로 치면 Node.js = JDK, npm = Gradle. 빌드 결과물은 HTML/CSS/JS 파일이고 브라우저가 실행한다. 배포 시 nginx가 그 파일을 서빙하면 되고 서버에 Node.js가 떠 있을 필요 없다.

## JDK, Gradle, Maven이 뭔가요?

**JDK**(Java Development Kit) = 자바 개발 도구 세트. 안에 컴파일러(javac, `.java` → `.class`), JVM(`.class`를 실행, OS 상관없이 동일하게), 표준 라이브러리(`String`, `List` 등)가 들어있다. 없으면 컴파일도 실행도 못 한다.

**Gradle / Maven** = 빌드 도구. 빌드란 소스를 실행 가능한 jar로 만드는 전 과정: 외부 라이브러리 내려받기(의존성 관리), 컴파일, 테스트, jar 묶기. 라이브러리 수십 개를 손으로 맞추는 건 불가능해서 필요하다.
- Maven: 구형. `pom.xml`에 XML. 장황하지만 정형화. 회사 구버전 프로젝트에서 볼 확률 높음.
- Gradle: 신형. `build.gradle`에 코드처럼. 짧고 빠름. Spring Boot 새 프로젝트 기본.

비유: JDK는 요리 도구와 기본 재료, Gradle/Maven은 레시피대로 장 봐오고 조리해서 접시에 담는 주방장.

## `.env`는 커밋 안 하는데 키를 바꾸면 어떻게 적용되나요? 빌드할 때 들어가나요?

**빌드할 때 들어가는 게 아니다. 실행할 때 들어간다.**
- jar 안에는 `${POLYGON_API_KEY}` 같은 빈칸만 있다. local과 prod의 jar는 완전히 같은 파일.
- 서버엔 `.env`가 따로 있다(SSH로 한 번 직접 만듦). Docker Compose가 앱을 띄울 때 `.env`를 읽어 컨테이너 환경변수로 넣고, Spring Boot가 시작하면서 빈칸을 채운다.
- 키를 바꾸려면 서버 `.env` 수정 후 앱 재시작. 빌드·배포 다시 안 한다.

이유: 같은 jar가 어디서든 돌아서 "내 PC에선 됐는데" 문제가 줄고, jar를 열어봐도 키가 없다. 이 원칙이 **12-Factor App**의 "설정은 코드가 아니라 환경에".

## Docker로 배포할 때 `.env`는 어디에 끼어 있나요?

`.env`는 **도커 이미지 안에 들어가지 않는다.** 서버 바닥(docker-compose.yml 옆)에 놓여 있고, Docker Compose가 컨테이너를 **띄우는 순간** 읽어서 각 컨테이너에 환경변수로 꽂아준다.

```
서버
├── docker-compose.yml   ← Git에서 받음
├── .env                 ← SSH로 직접 만듦, Git에 없음
└── Compose가 .env를 읽어 컨테이너마다 환경변수 주입
    ├── backend   POLYGON_API_KEY=...
    ├── analyzer  ANTHROPIC_API_KEY=...
    └── postgres  POSTGRES_PASSWORD=...
```

키 변경: 서버 `.env` 수정 → `docker compose restart backend`. 이미지는 그대로.

## 헥사고날 아키텍처가 뭔가요?

아이디어는 하나: **"핵심 로직이 바깥세상(DB, 외부 API, 메시지 앱)을 직접 알지 못하게 하자."** 바깥은 자주 바뀌고(Polygon→Finnhub, 텔레그램→카카오, Claude→Llama) 핵심 규칙은 안 바뀌기 때문.

- **포트(Port)**: 문. 핵심 로직이 "뉴스 가져올 뭔가가 필요해"라고 선언한 **interface**. 예: `NewsProvider.fetch(ticker, date)`.
- **어댑터(Adapter)**: 문에 꽂는 플러그. 실제로 외부와 통신하는 **구현체**. 예: `PolygonNewsProvider`. 갈아 끼울 수 있다.

비유: 핵심 로직은 노트북, 포트는 USB 단자, 어댑터는 거기 꽂는 마우스. 마우스를 바꿔도 노트북은 그대로.

전체 적용(DB 접근까지 포트로 감싸기)은 파일이 두 배가 되어 지금은 안 한다. `external/`의 외부 연동에만 적용.

## 에러 처리와 응답 형식, 쉽게

상황: 프론트가 `GET /stocks/AAPL/predictions`를 호출.

1. **성공 응답**: 찾은 데이터만 그대로 준다(`[{...}, {...}]`). "잘 됐다"는 HTTP 상태 코드 200이 말한다. `{success: true, data: ...}`로 감싸면 같은 말을 두 번 하는 것이고 프론트가 매번 한 겹 벗겨야 한다.
2. **에러 응답**: 모양을 하나로 통일해야 프론트가 에러 화면 코드를 한 번만 짠다. 직접 만들지 않고 세계 표준 **RFC 7807**(`title`, `status`, `detail`, `instance`)을 쓴다. Spring Boot 3 내장.
3. **에러를 잡는 위치**: 컨트롤러마다 `try-catch`하면 API 수만큼 반복. 대신 `@RestControllerAdvice`라는 **고객센터 클래스 하나**가 모든 예외를 받아 RFC 7807로 변환. 서비스는 `throw new StockNotFoundException(ticker)`만 하고 컨트롤러는 에러 코드가 없다. 예외 이름은 `RuntimeException`이 아니라 뭔지 아는 이름으로.
4. **외부 API 실패**(Polygon 죽음, Claude 타임아웃): 우리 잘못이 아니고 대부분 잠깐이다. 택배 비유: 몇 번 더 방문(재시도 3회, 1→2→4초) → 그래도 안 되면 다른 집 배송은 계속(실패 기록 후 다음 종목) → 나한테 부재중 문자(텔레그램 실패 알림). 조용히 죽는 게 가장 무서운 장애.

## `articles.raw`에 기사 본문이 들어가나요?

**아니다.** `raw`는 Polygon이 보내준 **API 응답 JSON 통째로**(제목, 짧은 설명, URL, 매체명, 감성 분석). 뉴스 API는 저작권 때문에 본문을 안 주고 링크만 준다.
- `raw` = API 응답 JSON. 남긴다.
- `content` = 기사 본문. 크롤링해야 얻는다. 지금은 안 하고 Llama 학습 직전에 붙인다.

본문 크롤링의 문제: 매체마다 HTML 구조가 달라 추출이 깨짐, 유료 매체는 로그인 벽, 크롤링 차단과 약관 문제, 파이프라인 실패 지점 추가.

## 마이그레이션이 뭔가요?

테이블 구조 변경 이력을 번호 붙인 SQL 파일로 관리하는 것. `V1__create_stocks.sql`, `V2__add_column.sql`처럼. 앱이 시작할 때 아직 안 적용된 번호를 순서대로 실행하고 어디까지 했는지 DB에 기록한다. 내 PC와 서버의 DB 구조를 항상 같게 유지하는 수단.
JPA `ddl-auto=update`는 Entity 보고 알아서 고치지만 기록이 안 남고 컬럼 변경 시 옛 컬럼을 방치해 prod에선 금기. 우리는 Flyway + `validate`.

## 멱등(idempotent)이 뭔가요?

같은 작업을 두 번 실행해도 결과가 한 번 실행한 것과 같다는 뜻. "오늘 예측이 이미 있으면 다시 만들지 않고 건너뛴다"처럼 짜두면, 실수로 두 번 눌러도 중복이 안 생기고 밀린 작업을 다시 돌려도 안전하다.

## 포트가 뭔가요? 인프라 구성도의 네 가지 규칙은 무슨 뜻인가요?

**포트** = 서버 한 대 안에서 프로그램마다 받는 문 번호. backend 8080, DB 5432, 웹 80·443, SSH 22.

1. **prod는 nginx 문만 밖으로 연다.** nginx는 아파트 정문 경비실. 외부 사람은 경비실로만 들어오고 backend·DB는 단지 안 통로(Docker 내부 네트워크)로만 연결된다. DB 문이 인터넷에 열리면 봇이 몇 분 안에 찾아내 비밀번호를 무작위로 두드린다.
2. **prod DB 데이터는 Docker 볼륨에.** 컨테이너는 일회용 도시락통이라 배포 때마다 버리고 새로 만든다. DB 파일이 컨테이너 안에 있으면 같이 버려진다. 볼륨은 컨테이너 밖 창고라서 새 컨테이너가 같은 창고에 연결된다.
3. **local은 DB 문 5432를 연다.** 내 PC는 공유기 뒤라 인터넷에서 직접 못 들어와 안전하고, 열어야 DBeaver로 테이블을 볼 수 있다. prod와 반대인 이유.
4. **장애 알림은 요약 알림과 다른 통로로.** 사용자 요약은 카카오톡, 관리자 장애 알림은 텔레그램. 카카오 토큰 만료로 실패했는데 그걸 카카오로 알리면 못 받는다.

## `PREDICT`를 바꾼다는 게 `predictions` 테이블을 없앤다는 건가요?

아니다. `predictions` 테이블은 그대로다. 바꾼 건 `job_runs`(작업 일지) 테이블의 **작업 이름 칸에 들어가는 값**이다.
저녁 작업은 LLM을 한 번 불러 요약과 예측을 같이 만드는데, 이름표가 `PREDICT`면 요약이 빠진 것처럼 보여서 `DAILY_ANALYSIS`로 바꿨다.

## `/me/stocks`로 만들면 나중에 `/users/{id}/stocks`로 바꿔야 하지 않나요?

아니다. **`/me`는 로그인을 붙인 뒤에도 그대로 쓰는 표준**이다.
- `/users/1/stocks`: 주소의 `1`을 믿는다. 로그인한 사람이 2번인데 주소를 1로 바꾸면 서버가 매번 "너 1번 맞아?"를 검사해야 하고, 한 군데만 빼먹어도 남의 데이터가 보인다. 실무에서 자주 나는 보안 사고.
- `/me/stocks`: 서버가 로그인 정보로 "너는 2번"을 스스로 정한다. 주소에 바꿔치기할 ID가 없다.

실제 예: GitHub API `GET /user`, Spotify API `GET /me`.
`/users/{id}`는 **남의 데이터를 보는 관리자 기능**용이다. 필요해지면 `/admin/users/{id}/...`를 따로 만들고 "관리자만" 권한을 건다. 둘은 대체 관계가 아니라 용도가 다른 두 개.

## Massive API 키는 주가만 가져오는 건가요?

아니다. 외부 데이터 대부분을 이 키 하나로 받는다. (설계서 3-5)

| 용도 | 쓰는 곳 |
|---|---|
| 종목 조회 | 관심 종목 추가 때 티커 검증, 회사명 |
| 뉴스 | 저녁 분석, 백필 |
| 일봉 주가 | 아침 채점, 백필 |
| 휴장일 | 주말·공휴일 작업 건너뛰기 |

무료 요금제 조건: 분당 5회, 과거 2년, 장 마감 후 일봉만(실시간 시세 없음).
Massive 밖에서 받는 것은 요약·예측(Claude)과 알림(텔레그램, 카카오)뿐.

## record에 `notify`라는 필드 이름을 쓰면 왜 컴파일 에러가 나나요?

record는 필드 이름 그대로 메서드를 만든다(`ticker` → `ticker()`). 그런데 모든 Java 객체는 `Object`를 물려받고, `Object`에는 이미 `notify()`(스레드끼리 신호 주는 메서드)가 있고 덮어쓸 수도 없다. 그래서 이름이 겹쳐 막힌다. 응답 필드를 `notifyEnabled`로 바꿨다.
일반 클래스 + Lombok `@Getter`는 `isNotify()`를 만들어서 겹치지 않는다. 그래서 Entity의 `notify` 필드는 괜찮다.
