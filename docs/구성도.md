# 구성도

> 설계서(`설계서.md`)의 결정을 그림으로 옮긴 문서. 설계가 바뀌면 이 문서도 함께 고친다.
> 그림은 Mermaid로 작성. GitHub에서는 자동으로 그림이 되고, VS Code는 "Markdown Preview Mermaid Support" 확장, IntelliJ는 마크다운 설정에서 Mermaid를 켜면 보인다.

## 1. 아키텍처 구성도

시스템의 부품과 연결. "무엇이 무엇을 부르는가".

```mermaid
flowchart LR
    user["사용자"]
    admin["관리자 (나)"]

    subgraph client["사용자 접점"]
        fe["React + TS<br/>(나중에)"]
        kakao["카카오톡<br/>사용자 요약 (운영)"]
        tg["텔레그램<br/>테스트 · 장애 알림"]
    end

    subgraph system["우리 시스템"]
        be["backend<br/>Spring Boot"]
        an["analyzer<br/>FastAPI"]
        db[("PostgreSQL")]
    end

    subgraph ext["외부 서비스"]
        polygon["Polygon (Massive)<br/>뉴스 · 주가 · 종목 조회 · 휴장일"]
        claude["Claude API"]
        llama["파인튜닝 Llama<br/>Ollama (나중에)"]
    end

    user --> fe
    fe -->|"REST API"| be
    be -->|"읽기 · 쓰기"| db
    be -->|"HTTP 분석 요청"| an
    an -.->|"읽기 전용<br/>학습 데이터 추출"| db
    an --> claude
    an -.-> llama
    be --> polygon
    be --> kakao
    be --> tg
    kakao --> user
    tg --> admin
```

읽는 법:
- 실선은 지금 만드는 것, 점선은 나중에 붙이는 것.
- DB 쓰기는 backend만 한다. analyzer는 학습 데이터를 뽑을 때만 읽는다.
- backend에서 외부로 나가는 선(Polygon, analyzer, 카카오, 텔레그램)은 전부 **포트/어댑터**(interface + 구현체)를 거친다. 그래서 Polygon을 Finnhub로, Claude를 Llama로 바꿔도 backend 핵심 로직은 그대로다.
- 사용자 요약과 장애 알림은 통로가 다르다. 카카오 토큰 만료가 장애 원인이면 카카오로는 장애 소식을 못 받기 때문.

## 2. 인프라 구성도

부품이 실제로 **어디서** 도는가. local과 prod를 따로 그린다.

### 2-1. local (내 PC)

```mermaid
flowchart TB
    subgraph pc["내 PC (Windows)"]
        ide["IntelliJ / VS Code"]
        dbeaver["DBeaver 등<br/>DB 클라이언트"]
        env[".env<br/>Git 제외"]
        subgraph compose["Docker Compose"]
            be["backend<br/>:8080"]
            an["analyzer<br/>:8000"]
            pg[("postgres<br/>:5432")]
        end
        vite["Vite 개발 서버<br/>:5173 (나중에)"]
    end

    ext["외부 API<br/>Polygon · Claude · 텔레그램"]

    env -.->|"실행 시 환경변수 주입"| compose
    ide -->|"코드 수정 · 디버깅"| be
    dbeaver -->|"5432 직접 조회"| pg
    be --> an
    be --> pg
    an -.-> pg
    vite -->|"/api 프록시"| be
    be --> ext
    an --> ext
```

- 프로파일: `local`. 스케줄은 꺼두고 수동 실행 API로만 돌린다. 알림은 텔레그램.
- postgres 5432를 PC에 열어 DB 클라이언트로 직접 본다. 내 PC는 공유기 뒤라 인터넷에서 직접 못 들어와서 안전하다.

### 2-2. prod (클라우드 VM)

```mermaid
flowchart TB
    internet(("인터넷"))
    me["나<br/>SSH"]

    subgraph vm["클라우드 VM (Oracle Always Free 1순위, Linux)"]
        fw{{"방화벽<br/>22 · 80 · 443만 열림"}}
        env[".env<br/>SSH로 직접 작성"]
        subgraph compose["Docker Compose 내부 네트워크"]
            nginx["nginx :80 / :443<br/>프론트 정적 파일 + /api 전달"]
            be["backend :8080"]
            an["analyzer :8000"]
            pg[("postgres :5432")]
        end
        vol[("Docker 볼륨<br/>DB 데이터 보관")]
    end

    ext["외부 API<br/>Polygon · Claude · 카카오 · 텔레그램"]

    internet -->|"80 / 443"| fw
    me -->|"22"| fw
    fw --> nginx
    nginx -->|"/api"| be
    be --> an
    be --> pg
    an -.-> pg
    pg --- vol
    env -.->|"실행 시 환경변수 주입"| compose
    be --> ext
    an --> ext
```

- 프로파일: `prod`. 스케줄 켜짐. 사용자 요약은 카카오톡, 장애 알림은 텔레그램.
- **밖에서 들어올 수 있는 건 nginx뿐.** backend, analyzer, postgres 포트는 VM 밖으로 안 연다. 아파트로 치면 nginx가 정문 경비실이고, 나머지는 단지 안 통로로만 연결된다.
- **DB 데이터는 Docker 볼륨에.** 컨테이너는 배포 때마다 버리고 새로 만드는 일회용이라, 볼륨 없이 두면 데이터도 같이 사라진다.
- `.env`는 이미지 안에 들어가지 않는다. VM 바닥에 있고 Compose가 컨테이너를 띄울 때 읽어서 주입한다.

## 3. 데이터 흐름도

하루 동안 무슨 일이 어떤 순서로 일어나는가.

### 3-1. 저녁 분석 작업 `DAILY_ANALYSIS` (KST 20:00, 미국 장 열리기 전)

뉴스를 모아 요약과 예측을 만든다. 사용자에게 보내는 건 3-3 발송 작업이 따로 한다.

```mermaid
sequenceDiagram
    autonumber
    participant S as 스케줄러
    participant B as backend
    participant DB as PostgreSQL
    participant P as Polygon
    participant A as analyzer
    participant C as Claude API
    participant T as 텔레그램 (관리자)

    S->>B: 20:00 KST 저녁 분석 시작
    B->>P: 오늘 밤 미국 장 휴장인지 확인
    alt 휴장일
        B->>DB: job_runs 생성 (SKIPPED, 휴장)
    else 거래일
        B->>DB: job_runs 생성 (RUNNING)
        B->>DB: 활성 종목 조회 (stocks.active = true)
        loop 종목마다
            B->>DB: 오늘 요약 이미 있나? (멱등 체크)
            alt 이미 있음
                B->>B: 건너뜀
            else 없음
                B->>P: 마지막 요약 이후 뉴스 요청
                P-->>B: 기사 목록
                B->>DB: 새 기사만 저장 (url 유니크)
                B->>A: 기사 묶음 + 분석 요청
                A->>C: 프롬프트 전송
                C-->>A: 핵심 기사 · 요약 · 예측 (JSON)
                A-->>B: 분석 결과
                B->>DB: summaries · summary_articles · predictions 저장
            end
        end
        Note over B,C: 외부 호출 실패 시 재시도 3회 (1→2→4초). 그래도 실패하면 그 종목만 실패로 기록하고 다음 종목 진행
        B->>DB: job_runs 갱신 (SUCCESS 또는 FAILED + stats)
        opt 실패한 종목이 있으면
            B->>T: 장애 알림
        end
    end
```

### 3-2. 아침 채점 작업 `SCORE` (KST 07:00, 미국 장 닫힌 뒤)

```mermaid
sequenceDiagram
    autonumber
    participant S as 스케줄러
    participant B as backend
    participant DB as PostgreSQL
    participant P as Polygon

    S->>B: 07:00 KST 채점 시작
    B->>B: 대상 날짜 = KST 어제 = 방금 닫힌 미국 장
    alt 대상 날짜가 휴장일
        B->>DB: job_runs 생성 (SKIPPED, 휴장)
    else 거래일
        B->>DB: job_runs 생성 (RUNNING)
        B->>P: 대상 날짜 일봉 요청 (활성 종목 전체)
        P-->>B: 시가 · 고가 · 저가 · 종가 · 거래량
        B->>DB: daily_prices 저장
        B->>DB: 채점 안 된 예측 조회
        loop 예측마다
            B->>B: 시가→종가 등락률 계산, ±0.5% 기준으로 실제 방향 판정
            B->>DB: prediction_results 저장 (hit 여부)
        end
        B->>DB: 관심 사용자 0명인 종목 active = false
        B->>DB: job_runs 갱신 (SUCCESS 또는 FAILED)
    end
```

### 3-3. 사용자별 발송 작업

저녁 분석이 만든 요약을 사용자마다 정한 시간에 보낸다. 요약은 종목당 한 번만 만들고 발송만 나눠 한다. 이 작업은 `job_runs`에 기록하지 않고, 이력은 `notification_logs`에 남는다.

```mermaid
sequenceDiagram
    autonumber
    participant S as 스케줄러
    participant B as backend
    participant DB as PostgreSQL
    participant K as 카카오톡

    S->>B: 발송 작업 (30분마다, 앱 시작 직후에도 한 번)
    B->>DB: 대상 조회 - 오늘(KST) 알림 시간이 이미 지났고, 오늘 SUCCESS 기록이 없는 사용자
    loop 사용자마다
        B->>DB: 관심 종목(notify = true)마다 가장 최근 요약 조회
        B->>K: 요약 묶어서 발송 (요약 생성 시각 표시)
        alt 성공
            B->>DB: notification_logs 저장 (SUCCESS)
        else 실패
            B->>DB: notification_logs 저장 (FAILED + 이유)
        end
    end
    Note over B,DB: 실패한 사용자는 다음 30분에 다시 대상이 된다. 날짜가 바뀌면 전날 못 보낸 건 보내지 않는다. 성공은 부분 유니크 인덱스로 하루 하나만 들어간다
```

### 3-4. 앱 시작 시 따라잡기

```mermaid
sequenceDiagram
    autonumber
    participant B as backend
    participant DB as PostgreSQL
    participant P as Polygon

    B->>DB: 작업별 마지막 처리 날짜 조회 (SUCCESS 또는 SKIPPED)
    B->>B: 오늘까지 빠진 날짜 계산
    loop 빠진 날짜마다 (오래된 날짜부터)
        alt 휴장일
            B->>DB: job_runs SKIPPED 기록
        else 거래일
            B->>P: 그날 뉴스 · 일봉 요청
            B->>DB: articles · daily_prices 저장
            B->>DB: 그날 채점
        end
    end
    Note over B: 요약과 예측은 따라잡지 않는다. 지나간 날짜로 만들면 그 사이 뉴스에 결과가 섞여 데이터 누수가 생긴다
```

### 3-5. 백필 `BACKFILL` (최초 1회, 수동)

과거 2년치 뉴스와 일봉을 한꺼번에 저장한다. Claude를 거치지 않는다. 수동 실행 API로 시작하고 `job_runs`에 `BACKFILL`로 기록한다. Polygon 무료 티어(분당 5회)에 맞춰 요청 사이에 간격을 둔다.

## 4. ERD

```mermaid
erDiagram
    users ||--o{ user_stocks : "관심 등록"
    stocks ||--o{ user_stocks : "관심 대상"
    stocks ||--o{ stock_articles : "관련 기사"
    articles ||--o{ stock_articles : "관련 종목"
    stocks ||--o{ summaries : "거래일마다 하나"
    summaries ||--o{ summary_articles : "핵심 기사"
    articles ||--o{ summary_articles : "근거로 쓰임"
    summaries ||--o| predictions : "0 또는 1"
    predictions ||--o| prediction_results : "채점"
    stocks ||--o{ daily_prices : "일봉"
    users ||--o{ notification_logs : "발송 기록"

    users {
        bigint id PK
        varchar email UK
        varchar nickname
        varchar role "USER / ADMIN"
        varchar telegram_chat_id "null 허용"
        time notify_time "요약 받을 시각 KST 30분 단위"
        timestamptz created_at
        timestamptz deleted_at "소프트 삭제"
    }
    user_stocks {
        bigint user_id PK, FK
        bigint stock_id PK, FK
        boolean notify
        timestamptz created_at
        timestamptz deleted_at "소프트 삭제"
    }
    stocks {
        bigint id PK
        varchar ticker UK
        varchar name
        boolean active "시스템 수집 대상"
        timestamptz created_at
        timestamptz deleted_at "소프트 삭제"
    }
    articles {
        bigint id PK
        text url UK
        text title
        text description
        varchar source
        timestamptz published_at
        varchar provider "POLYGON / FINNHUB"
        jsonb raw "API 응답 JSON"
        timestamptz created_at
    }
    stock_articles {
        bigint stock_id PK, FK
        bigint article_id PK, FK
    }
    summaries {
        bigint id PK
        bigint stock_id FK "target_date와 함께 유니크"
        date target_date
        text body "요약 문단"
        varchar model_name
        varchar prompt_version
        jsonb raw_response "LLM 응답 JSON"
        timestamptz created_at
    }
    summary_articles {
        bigint summary_id PK, FK
        bigint article_id PK, FK
        smallint rank
    }
    predictions {
        bigint id PK
        bigint summary_id FK, UK
        varchar direction "UP / DOWN / NEUTRAL"
        numeric confidence
        text reasoning
        timestamptz created_at
    }
    prediction_results {
        bigint prediction_id PK, FK
        numeric open_price
        numeric close_price
        numeric change_pct
        varchar actual_direction
        boolean hit
        timestamptz scored_at
    }
    daily_prices {
        bigint id PK
        bigint stock_id FK "trade_date와 함께 유니크"
        date trade_date
        numeric open
        numeric high
        numeric low
        numeric close
        bigint volume
        timestamptz created_at
    }
    notification_logs {
        bigint id PK
        bigint user_id FK "notify_date와 함께 성공만 유니크"
        date notify_date "발송 날짜 KST"
        varchar channel "KAKAO / TELEGRAM"
        varchar status "SUCCESS / FAILED"
        text error_message
        timestamptz created_at
    }
    job_runs {
        bigint id PK
        varchar job_name "DAILY_ANALYSIS / SCORE / COLLECT / BACKFILL"
        date target_date
        varchar status "RUNNING / SUCCESS / FAILED / SKIPPED"
        timestamptz started_at
        timestamptz finished_at
        jsonb stats
        text error_message
    }
```

`job_runs`는 다른 테이블과 연결이 없는 독립 테이블이다. 인덱스 목록은 설계서 4-11 참고.
